# University Navigator — راهنمای دانشگاه

نمونهٔ اولیهٔ (MVP) یک سامانهٔ مسیریابی سه‌بعدی برای دانشگاه: **پردیس و ساختمان‌ها یک نقشه‌اند.** کاربر استاد، اتاق یا ساختمان را جستجو می‌کند و یک مسیر پیوسته می‌گیرد: از درب ورود دانشگاه، از میان حیاط تا در ساختمان ورودی، داخل آن (راه‌پله، راهرو) و از روی پل‌های هوایی تا در اتاق. مدیران و ویرایشگران مجاز، داده‌ها را از یک پنل محدود مدیریت می‌کنند.

> **توجه — دقت داده‌ها.** پلان محوطه از نقشهٔ CAD است. **چیدمان داخلی طبقهٔ اول ساختمان‌های ۱، ۲ و ۳ طراحی شده است** (از روی کروکی‌های دست‌نویس و شکل پلان هر ساختمان در نقشهٔ کلی) و برداشت دقیق نیست. نام اساتید و شمارهٔ اتاق‌ها از عکس کم‌کیفیت دست‌خط خوانده شده و بیشترشان با اطمینان پایین علامت خورده‌اند؛ پیش از اتکا باید بازبینی شوند. ارتفاع ساختمان‌ها تقریبی (تعداد طبقه × ۳٫۶ متر) و حوض و درخت‌ها نمادین‌اند.

## ویژگی‌ها

- رابط فارسی‌محور و کاملاً راست‌به‌چپ (`lang="fa" dir="rtl"`)، فونت Vazirmatn، آیکون‌های Lucide.
- **یک صفحهٔ پردیس** (`/campus`) برای نقشه، جستجو و مسیریابی. صفحه‌های قدیمی `/buildings/[slug]` و `/directions` به همین صفحه هدایت می‌شوند.
- صحنهٔ سه‌بعدی پردیس بر پایهٔ نقشهٔ CAD: پلان واقعی ساختمان‌ها، پارک با حوض، درخت، الاچیق‌های دایره‌ای و مربعی (جای آن‌ها از نقشه و علامت‌گذاری مالک)، زمین چمن و ورزشی، «درب ورود»، درهای علامت‌گذاری‌شدهٔ مالک. ساختمان‌هایی که خط پیرامون بسته ندارند (۱۲، ۱۳ و ۱۵) با پین نشان داده می‌شوند. بخش سبز نقشه فضای باز است و اتاقی ندارد.
- **طبقهٔ اول ساختمان‌های ۱، ۲ و ۳** با راهروها و اتاق‌های قابل آدرس‌دهی، و دو پل هوایی: ۳ ↔ ۲ و ۲ ↔ ۱. ورودی ساختمان ۳ و ورودی ساختمان ۱ از حیاط است؛ ساختمان ۲ در حیاط در ندارد و فقط از پل‌ها می‌شود وارد آن شد. با گزینهٔ «نمای داخلی» همهٔ این طبقه‌ها بدون سقف دیده می‌شوند.
- جستجوی فارسی (ي/ی، ك/ک، ارقام فارسی/عربی/لاتین، فاصله و نیم‌فاصله) بر اساس نام استاد، شمارهٔ اتاق، ساختمان و کلیدواژه؛ نمونه: «دفتر ۴۳۰ ساختمان ۲ علیرضا حریری ایرج».
- **مسیر یکپارچه**: پیاده‌روی بیرونی از درب دانشگاه (گراف دید + Dijkstra با دورزدن ساختمان‌ها) تا در ساختمان ورودی، سپس مسیر داخلی (A\* روی گراف طبقه‌ها، با یال‌های `door`، `stairs` و `bridge`) تا اتاق. اتاقی که ساختمانش در حیاط در دارد از همان ساختمان وارد می‌شود؛ اتاق‌های ساختمان ۲ از نزدیک‌ترین ساختمان ورودی و پل هوایی. راهنمای مرحله‌به‌مرحلهٔ فارسی، مجموع متر و زمان تقریبی، و رسم مسیر روی صحنه (بیرون و داخل).
- صفحهٔ واحد `/departments/[slug]` با «نمایش روی نقشه»؛ فیلدهای نامشخص «اطلاعات ثبت نشده» نشان داده می‌شوند (هیچ تلفن یا ساعت کاری ساختگی وجود ندارد).
- تشخیص WebGL و حالت جایگزین (جستجو و اطلاعات مقصد بدون سه‌بعدی هم کار می‌کنند)، Error Boundary، حالت‌های بارگذاری.
- Supabase (PostgreSQL + Auth + RLS) به‌صورت اختیاری؛ پنل مدیریت با نقش‌های `admin` و `editor`.

## فناوری‌ها

Next.js 16 (App Router) · React 19 · TypeScript (strict) · Tailwind CSS 4 · Lucide React · Three.js 0.187 · @react-three/fiber 9 · @react-three/drei 10 · Supabase (`@supabase/supabase-js`, `@supabase/ssr`) · Zod 4 · Vitest 5.

نسخه‌های دقیق در `package.json` پین شده‌اند و `package-lock.json` کامیت می‌شود.

## پیش‌نیازها و نسخهٔ Node

| مورد | مقدار |
| --- | --- |
| حداقل Node (`engines` در `package.json`) | `>=22.12.0` |
| نسخهٔ پیشنهادی | **Node 22** (`.nvmrc` = `22`) |
| آنچه واقعاً آزموده شد | Node **v22.23.5** با npm 10.9.9 |

نکته: خودِ Next.js 16 با Node 20.9+ هم کار می‌کند، اما ابزار آزمون (Vitest 5.1.1) به Node `^22.12 || ^24 || >=26` نیاز دارد؛ به‌همین دلیل `engines` روی `>=22.12.0` تنظیم شده است تا `npm run test` همیشه قابل اجرا باشد.

## توسعهٔ محلی

```bash
npm run dev        # http://localhost:3000
```

`predev` و `prebuild` اسکریپت `scripts/copy-draco.mjs` را اجرا می‌کنند که دیکودر Draco را از `node_modules/three` به `public/draco/` کپی می‌کند (این پوشه در Git نادیده گرفته می‌شود).

اسکریپت‌های دیگر:

| دستور | کار |
| --- | --- |
| `npm run lint` | ESLint |
| `npm run typecheck` | `tsc --noEmit` |
| `npm run test` | `vitest run` |
| `npm run build` / `npm run start` | ساخت تولیدی و اجرای آن |
| `python3 scripts/cad/build_interiors.py` | تولید `data/indoor/*.json` از `data/campus/campus-layout.json`، `scripts/cad/floorplans.py` و `scripts/cad/campus-offices.json` |
| `node scripts/generate-seed-sql.mjs` | تولید `database/seed.sql` از `data/indoor/*.json` |

## تنظیم متغیرهای محیطی

فایل `.env.local.example` را به `.env.local` کپی کنید (`.env.local` در Git نادیده گرفته می‌شود):

| متغیر | توضیح |
| --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | نشانی پروژهٔ Supabase (اختیاری) |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | کلید عمومی anon (اختیاری؛ دسترسی را RLS محدود می‌کند) |
| `NEXT_PUBLIC_DATA_MODE` | `demo` (پیش‌فرض: داده از فایل‌های محلی `data/indoor`) یا `supabase` (داده از Supabase؛ نیازمند دو مقدار بالا) |
| `NEXT_PUBLIC_DEMO_ADMIN` | `true` فقط برای پنل آزمایشی محلی در توسعه؛ پیش‌فرض `false` |

این برنامه **هیچ کلید service-role** استفاده نمی‌کند و هیچ رمز یا راز سروری لازم نیست. هرگز کلید service-role را در متغیر `NEXT_PUBLIC_*` یا کد کلاینت نگذارید.

## داده‌های محلی و پنل مدیریت

بدون هیچ تنظیمی، سایت با فایل‌های محلی `data/campus/campus-layout.json` و `data/indoor/*.json` کار می‌کند. داده‌ها هنگام بارگذاری با Zod اعتبارسنجی می‌شوند.

پنل `/admin` بدون Supabase، صفحهٔ «راه‌اندازی لازم است» را نشان می‌دهد. یک **حالت فقط‌توسعهٔ محلی** هم هست: وقتی `NODE_ENV=development` و `NEXT_PUBLIC_DEMO_ADMIN=true` و Supabase در حال استفاده نباشد، پنل بدون ورود باز می‌شود و ویرایش‌ها فقط در `localStorage` همین مرورگر ذخیره می‌شوند (موقت و محلی). این حالت **هیچ امنیتی ندارد**، رمز ثابت ندارد و در build تولیدی هرگز فعال نمی‌شود (در `src/lib/config.ts` به `NODE_ENV === "development"` گره خورده است).

## افزودن یا اصلاح اتاق و استاد

۱. نام‌ها و شمارهٔ اتاق‌ها در `scripts/cad/campus-offices.json` هستند (هر اتاق: شماره، استادها، گروه، `confidence`). اصلاح کنید و `python3 scripts/cad/build_interiors.py` را اجرا کنید؛ `data/indoor/*.json` دوباره ساخته می‌شود (و در صورت نیاز `node scripts/generate-seed-sql.mjs`).
۲. چیدمان (محل راهروها و اتاق‌ها به متر، داخل پلان هر ساختمان) در `scripts/cad/floorplans.py` است و از روی کروکی‌های دست‌کشیده نوشته شده: راهروی پله‌ای و بازوی غربی در ساختمان ۱، دو بال و سالن میانی در ساختمان ۲، راهروی بلند و راهروی شمالی‌جنوبی در ساختمان ۳. سازنده آن را روی شکل واقعی ساختمان (`campus-layout.json`) برش می‌دهد و در، گراف مسیر و ورودی پل‌ها را می‌سازد. برای تغییر جای یک اتاق یا راهرو فقط مختصات همان‌جا را عوض کنید.
۳. شناسه‌ها پایدارند: ساختمان `campus-bN`، اتاق `campus-bN-r<شماره>`، واحد `prof-campus-bN-<شماره>-<i>`.

## افزودن طبقه یا ساختمان

ردیف‌های `buildings`، `floors`، `rooms`، `navigation_nodes`، `navigation_edges`، `entrances` و `departments` لازم است (طبقه با `elevation` به متر و یال `stairs` به طبقهٔ مجاور؛ پل بین ساختمان‌ها یال `bridge`) و ساختمان باید در `data/campus/campus-layout.json` به ورودی همان شماره در پلان محوطه وصل شود (`id` = `campus-bN`). راهنمای کامل: `docs/navigation-guide.md`، `docs/3d-model-guide.md` و `docs/cad-import-guide.md`.

## پیکربندی Supabase

۱. پروژه بسازید؛ (اگر پایگاه از نسخهٔ قدیمی‌تر ساخته شده، ابتدا `database/migrations/001-bridge-edge-type.sql`) در SQL Editor ابتدا `database/schema.sql` و سپس (اختیاری، داده‌های طبقهٔ اول ساختمان‌های ۱ تا ۳) `database/seed.sql` را اجرا کنید.
۲. `NEXT_PUBLIC_SUPABASE_URL` و `NEXT_PUBLIC_SUPABASE_ANON_KEY` را در `.env.local` بگذارید و `NEXT_PUBLIC_DATA_MODE=supabase` را تنظیم کنید.
۳. اگر Supabase در دسترس نباشد، برنامه به داده‌های محلی برمی‌گردد و خطای فنی را به کاربر نشان نمی‌دهد.

سیاست‌های RLS: بازدیدکنندگان (anon) فقط ردیف‌های فعال/منتشرشده را می‌خوانند و نمی‌توانند بنویسند؛ `editor` واحدها، خدمات و اتاق‌ها را می‌نویسد؛ `admin` همهٔ جدول‌ها و `profiles` را. نقش همیشه در پایگاه داده از `public.profiles` خوانده می‌شود، نه از مرورگر. جزئیات: `docs/architecture.md` و `docs/deployment-guide.md`.

## پیکربندی دسترسی مدیر

فقط یک `admin` می‌تواند ردیف `profiles` بسازد، پس اولین مدیر را باید یک بار از SQL Editor (که با نقش مالک اجرا می‌شود) ثبت کنید:

1. در Supabase → Authentication کاربری بسازید (ایمیل + گذرواژهٔ قوی).
2. در SQL Editor:

```sql
insert into public.profiles (user_id, full_name, role)
select id, 'نام مدیر', 'admin'
from auth.users
where email = 'admin@example.org';   -- ایمیل واقعی را جایگزین کنید
```

سپس از `/admin/login` وارد شوید. ویرایشگران را همین‌طور با `role = 'editor'` ثبت کنید. گذرواژه یا رمز ثابتی در مخزن وجود ندارد.

## آزمون و ساخت تولیدی

```bash
npm run typecheck
npm run lint
npm run test
npm run build
npm run start
```

آزمون‌های موجود در `tests/` (Vitest، محیط Node):

- `tests/data` — اعتبارسنجی Zod و ارجاعات داده‌های `data/indoor`
- `tests/search` — نرمال‌سازی فارسی و جستجو
- `tests/navigation` — A\*، مسیر چندطبقه، پل هوایی، مسیر بدون پله، حالت «مسیر وجود ندارد»، مسیر بیرونی و درهای ساختمان
- `tests/model` — پلان پردیس، مسیر یکپارچه از درب دانشگاه تا اتاق (از جمله اتاق ۴۳۰ ساختمان ۲ از طریق پل)، وضعیت نمایشگر
- `tests/3d` — رندر واقعی صحنهٔ React Three Fiber با `@react-three/test-renderer` (بدون GPU): ساختمان‌ها، طبقهٔ اول، پل‌ها، انتخاب اتاق، مسیر داخلی
- `tests/security` — قواعد دسترسی ادمین، غیرفعال‌بودن حالت محلی ادمین در production، وجود و منطق سیاست‌های RLS در `database/schema.sql`، نبود کلید service-role/رمز ثابت در کد
- `tests/theme.test.ts` — هم‌ترازی توکن‌های CSS و Three.js

محدودیت‌ها: رندر تصویری GPU/WebGL و رفتار لمسی با آزمون خودکار پوشش داده نمی‌شود (مسیرهای کاربری در Chrome headless به‌صورت دستی بررسی شد، نه به‌عنوان e2e داخل مخزن). سیاست‌های RLS فقط به‌صورت ایستا (تحلیل متن SQL) آزموده می‌شوند، نه روی پایگاه‌دادهٔ زنده.

## محدودیت‌های فعلی

- نام اساتید و شمارهٔ اتاق‌ها از دست‌خط کم‌کیفیت خوانده شده‌اند (بیشترشان `confidence: low`)؛ بازبینی لازم است.
- چیدمان داخلی از روی کروکی‌های دست‌کشیده (غیرمقیاسی) و با اندازه‌های تخمینی ساخته شده، نه برداشت‌شده؛ فقط طبقهٔ اول ساختمان‌های ۱ تا ۳ دارد. ساختمان‌های دیگر هنوز نقشهٔ داخلی ندارند و مسیر تا نزدیک‌ترین ضلع آن‌ها می‌رود.
- مسیر حیاط تقریبی است (پیاده‌رو در نقشهٔ CAD نیست).
- ارتفاع ساختمان‌ها تخمینی و ۱۲، ۱۳ و ۱۵ فقط پین‌اند؛ حوض و درخت‌ها نمادین‌اند.
- موقعیت‌یابی زنده (GPS) وجود ندارد؛ مسیر همیشه از درب ورود دانشگاه شروع می‌شود.
- حالت محلی پنل ادمین فقط برای توسعه است، امنیت ندارد و در تولید کار نمی‌کند.
- ویرایشگر بصری گراف مسیر نیست؛ گره‌ها و یال‌ها با جدول/فرم اعتبارسنجی‌شده ویرایش می‌شوند.
