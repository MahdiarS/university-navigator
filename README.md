# University Navigator — راهنمای دانشگاه

نمونهٔ اولیهٔ (MVP) یک سامانهٔ مسیریابی داخلی سه‌بعدی برای دانشگاه: دانشجویان و بازدیدکنندگان می‌توانند دفاتر اداری و امکانات را جستجو کنند، ساختمان را در نمای ایزومتریک سه‌بعدی ببینند، طبقات را از هم باز کنند (Exploded View) و از یک نقطهٔ شروع تا مقصد مسیر داخلی بگیرند. مدیران و ویرایشگران مجاز، داده‌ها را از یک پنل محدود مدیریت می‌کنند.

> **توجه — داده‌ها نمونه‌اند.** ساختمان، طبقات، اتاق‌ها، واحدها و مسیرهای این مخزن **کاملاً فرضی (دمو)** هستند و اطلاعات رسمی دانشگاه نیستند. تا زمانی که نقشه‌های واقعی (DWG/DXF) و داده‌های تأییدشده فراهم نشود، همه‌چیز با یک ساختمان پروسیجرال نمونه نمایش داده می‌شود و در رابط کاربری با نشان «دمو» مشخص شده است.

## ویژگی‌ها

- رابط فارسی‌محور و کاملاً راست‌به‌چپ (`lang="fa" dir="rtl"`)، فونت Vazirmatn، آیکون‌های Lucide.
- نمایشگر سه‌بعدی ساختمان با React Three Fiber و دوربین ارتوگرافیک ایزومتریک: چرخش، بزرگ‌نمایی، جابه‌جایی، بازنشانی دوربین.
- انتخاب طبقه (همه / همکف / اول / دوم)، حالت «جداسازی» طبقات با اسلایدر فاصله و انیمیشن نرم، نمایش نیمه‌شفاف یا پنهان‌کردن طبقات دیگر.
- اتاق‌های قابل انتخاب (hover / click)، پنل اطلاعات اتاق، هایلایت مقصد.
- راهرو، پله و آسانسور در مدل نمونه؛ ورودی اصلی ساختمان.
- موتور مسیریابی مستقل از رندرر: گراف + A\* (با Dijkstra برای مقایسه/جایگزین)، مسیر هم‌طبقه و چندطبقه، مسیر از ورودی، مسیر بدون پله (step-free) فقط بر اساس یال‌هایی که در داده صراحتاً `accessible` هستند، و پیام روشن در صورت نبودن مسیر.
- رسم مسیر روی صحنهٔ سه‌بعدی (برش‌های هر طبقه، نقاط انتقال پله/آسانسور) و راهنمای مرحله‌به‌مرحلهٔ فارسی. نقطهٔ شروع را کاربر **دستی** انتخاب می‌کند (موقعیت‌یابی زنده/GPS وجود ندارد).
- جستجو در `/search` با نرمال‌سازی فارسی (ي/ی، ك/ک، ارقام فارسی/عربی/لاتین، فاصله و نیم‌فاصله) بر اساس نام واحد، خدمت، شمارهٔ اتاق، طبقه، ساختمان و کلیدواژه.
- صفحهٔ واحد `/departments/[slug]` با دکمه‌های «نمایش روی نقشه» و «مسیریابی به این واحد»؛ فیلدهای نامشخص به‌صورت «موجود نیست» نمایش داده می‌شوند (هیچ شمارهٔ تماس یا ساعت کاری ساختگی نمایش داده نمی‌شود).
- صحنهٔ سه‌بعدی پردیس در `/campus` بر اساس نقشهٔ CAD محوطه: پلان واقعی ساختمان‌ها، فضای سبز، زمین ورزشی، دو «درب ورود»، انتخاب با کلیک یا از فهرست. ساختمان‌هایی که خط پیرامون بسته ندارند با پین نشان داده می‌شوند (پیرامون باز نمازخانه، ۷، به‌صورت خودکار بسته می‌شود) و ارتفاع‌ها تقریبی‌اند. محوطه سه‌بعدی کامل است: چمن ضخیم، پارک با حوض، درخت، الاچیق، زمین چمن و زمین ورزشی. حوض، درخت‌ها و الاچیق‌ها نمادین‌اند و در نقشهٔ CAD نیستند. مسیر پیاده از «درب ورود» دانشگاه تا هر ساختمان محاسبه و روی نقشه و به‌صورت مرحله‌ای نمایش داده می‌شود (تقریبی: پیاده‌رو و درِ ساختمان‌ها در نقشه نیست).
- بارگذار GLB (Mode B) که مسیرها را از `data/demo/model-manifest.json` می‌خواند و در صورت نبودن/خرابی فایل به مدل پروسیجرال برمی‌گردد.
- تشخیص WebGL و حالت جایگزین (جستجو و اطلاعات مقصد بدون سه‌بعدی هم کار می‌کنند)، Error Boundary، حالت‌های بارگذاری.
- Supabase (PostgreSQL + Auth + RLS) به‌صورت اختیاری؛ پنل مدیریت با نقش‌های `admin` و `editor`.

## فناوری‌ها

Next.js 16 (App Router) · React 19 · TypeScript (strict) · Tailwind CSS 4 · Lucide React · Three.js 0.187 · @react-three/fiber 9 · @react-three/drei 10 · Supabase (`@supabase/supabase-js`, `@supabase/ssr`) · Zod 4 · Vitest 5.

نسخه‌های دقیق در `package.json` پین شده‌اند و `package-lock.json` کامیت می‌شود.

## پیش‌نیازها و نسخهٔ Node

| مورد | مقدار |
| --- | --- |
| حداقل Node (`engines` در `package.json`) | `>=22.12.0` |
| نسخهٔ پیشنهادی | **Node 22** (`.nvmrc` = `22`) |
| آنچه واقعاً آزموده شد | Node **v22.23.5** با npm 10.9.9 |

نکته: خودِ Next.js 16 با Node 20.9+ هم کار می‌کند، اما ابزار آزمون (Vitest 5.1.1) به Node `^22.12 || ^24 || >=26` نیاز دارد؛ به‌همین دلیل `engines` روی `>=22.12.0` تنظیم شده است تا `npm run test` همیشه قابل اجرا باشد.

## تنظیم متغیرهای محیطی

فایل `.env.local.example` را به `.env.local` کپی کنید (`.env.local` در Git نادیده گرفته می‌شود):

| متغیر | توضیح |
| --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | نشانی پروژهٔ Supabase (اختیاری) |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | کلید عمومی anon (اختیاری؛ دسترسی را RLS محدود می‌کند) |
| `NEXT_PUBLIC_DATA_MODE` | `demo` (پیش‌فرض: داده از `data/demo`) یا `supabase` (داده از Supabase؛ نیازمند دو مقدار بالا) |
| `NEXT_PUBLIC_DEMO_ADMIN` | `true` فقط برای پنل آزمایشی محلی در توسعه؛ پیش‌فرض `false` |

این برنامه **هیچ کلید service-role** استفاده نمی‌کند و هیچ رمز یا راز سروری لازم نیست. هرگز کلید service-role را در متغیر `NEXT_PUBLIC_*` یا کد کلاینت نگذارید.

## حالت دمو

بدون هیچ تنظیمی، سایت عمومی با داده‌های `data/demo/*.json` و مدل پروسیجرال کار می‌کند (جستجو، نمایشگر سه‌بعدی، مسیریابی، صفحهٔ واحدها). داده‌ها هنگام بارگذاری با Zod اعتبارسنجی می‌شوند.

پنل `/admin` بدون Supabase، صفحهٔ «راه‌اندازی لازم است» را نشان می‌دهد. یک **حالت دمو فقط‌توسعه** هم هست: وقتی `NODE_ENV=development` و `NEXT_PUBLIC_DEMO_ADMIN=true` و Supabase در حال استفاده نباشد، پنل بدون ورود باز می‌شود و ویرایش‌ها فقط در `localStorage` همین مرورگر ذخیره می‌شوند (موقت و محلی). این حالت **هیچ امنیتی ندارد**، رمز ثابت ندارد و در build تولیدی هرگز فعال نمی‌شود (در `src/lib/config.ts` به `NODE_ENV === "development"` گره خورده است).

## افزودن ساختمان

۱. **داده**: ردیف‌های `buildings`، `floors`، `rooms`، `navigation_nodes`، `navigation_edges`، `entrances` (و در صورت نیاز `departments`, `department_services`, `facilities`) را اضافه کنید — در حالت دمو در فایل‌های `data/demo/*.json`، در حالت Supabase از پنل `/admin` یا SQL. شناسه‌ها باید پایدار باشند (`^[A-Za-z0-9][A-Za-z0-9_-]*$`) و `slug` ساختمان حروف کوچک و خط تیره.
۲. **مانیفست مدل**: یک عنصر به آرایهٔ `buildings` در `data/demo/model-manifest.json` اضافه کنید (`buildingId`، `exterior`، `floors`، `objectMap`، و بلوک `procedural`). بدون ورودی مانیفست، صفحهٔ `/buildings/<slug>` پیام «مدل سه‌بعدی ثبت نشده» نشان می‌دهد. مانیفست در Supabase ذخیره نمی‌شود و همیشه از همین فایل محلی خوانده می‌شود. فیلد `procedural` طبق طرح Zod الزامی است (حتی برای ساختمانی که GLB دارد).
۳. در صورت نیاز ساختمان را در `data/campus/campus-layout.json` به ورودی همان شماره در پلان محوطه وصل کنید (`slug` و `buildingId`)؛ این فایل با `scripts/cad/build_campus.py` تولید می‌شود (راهنما: `docs/cad-import-guide.md`).

در حال حاضر صفحهٔ خانه و بقیهٔ UI برای «ساختمان پایلوت» روی slug `building-01` (`PILOT_BUILDING_SLUG` در `src/lib/brand.ts`) تنظیم شده‌اند.

## افزودن طبقه

ردیف جدید در `floors` (با `floorNumber` یکتا در همان ساختمان و `elevation` به متر برای سطح پیاده‌روی)، یک ورودی در `buildings[].floors` مانیفست، اتاق‌ها و گره‌های مسیریابی همان طبقه با مختصات Y برابر `elevation`، و یال‌های `stairs`/`elevator` به طبقهٔ مجاور. برای مدل پروسیجرال، چیدمان اتاق‌ها در `procedural.rooms` هم لازم است. جزئیات در `docs/navigation-guide.md` و `docs/3d-model-guide.md`.

## جایگزینی مدل با GLB واقعی

۱. فایل‌ها را در `public/models/building-01/floors/floor-00.glb` و … (و در صورت وجود `exterior.glb`) بگذارید؛ هیچ GLB خالی/ساختگی نسازید.
۲. در `model-manifest.json` مقدار `status` هر فایل را به `"available"` تغییر دهید و `objectMap` را (نام mesh ← شناسهٔ اتاق) کامل کنید.
۳. نام هر mesh اتاق باید دقیقاً با `model_object_id` اتاق برابر باشد (مثلاً `ROOM_B01_F01_R03`).

مدل هر طبقه باید در **همان دستگاه مختصات ساختمان** (متر، Y = ارتفاع واقعی شامل `elevation` طبقه) صادر شود. فقط طبقه‌ای که نمایش داده می‌شود دانلود می‌شود و اگر بارگذاری شکست بخورد همان طبقه با مدل پروسیجرال نمایش داده می‌شود. راهنمای کامل: `docs/3d-model-guide.md`. فایل `exterior.glb` در مانیفست ثبت می‌شود، ولی نمایشگر فعلی هنوز آن را رندر نمی‌کند.

## پیکربندی Supabase

۱. پروژه بسازید؛ در SQL Editor ابتدا `database/schema.sql` و سپس (اختیاری، دادهٔ دمو) `database/seed.sql` را اجرا کنید.
۲. `NEXT_PUBLIC_SUPABASE_URL` و `NEXT_PUBLIC_SUPABASE_ANON_KEY` را در `.env.local` بگذارید و `NEXT_PUBLIC_DATA_MODE=supabase` را تنظیم کنید.
۳. اگر Supabase در دسترس نباشد، برنامه به داده‌های دمو برمی‌گردد و خطای فنی را به کاربر نشان نمی‌دهد.

سیاست‌های RLS: بازدیدکنندگان (anon) فقط ردیف‌های فعال/منتشرشده را می‌خوانند و نمی‌توانند بنویسند؛ `editor` واحدها، خدمات و اتاق‌ها را می‌نویسد؛ `admin` همهٔ جدول‌ها و `profiles` را. نقش همیشه در پایگاه داده از `public.profiles` خوانده می‌شود، نه از مرورگر. جزئیات: `docs/architecture.md` و `docs/deployment-guide.md`.

## پیکربندی دسترسی مدیر

فقط یک `admin` می‌تواند ردیف `profiles` بسازد، پس اولین مدیر را باید یک بار از SQL Editor (که با نقش مالک اجرا می‌شود) ثبت کنید:

1. در Supabase → Authentication کاربری بسازید (ایمیل + گذرواژهٔ قوی).
2. در SQL Editor:

```sql
insert into public.profiles (user_id, full_name, role)
select id, 'نام مدیر', 'admin'
from auth.users
where email = 'admin@example.org';   -- ایمیل واقعی را جایگزین کنید
```

سپس از `/admin/login` وارد شوید. ویرایشگران را همین‌طور با `role = 'editor'` ثبت کنید. گذرواژه یا رمز ثابتی در مخزن وجود ندارد.

## آزمون و ساخت تولیدی

```bash
npm run typecheck
npm run lint
npm run test
npm run build
npm run start
```

آزمون‌های موجود در `tests/` (Vitest، محیط Node):

- `tests/data` — داده‌های دمو، ارجاعات و اعتبارسنجی Zod
- `tests/search` — نرمال‌سازی فارسی و جستجو
- `tests/navigation` — A\*، مسیر هم‌طبقه/چندطبقه/از ورودی، مسیر بدون پله، حالت «مسیر وجود ندارد»، جایگزینی مسیر با تغییر مقصد
- `tests/model` — مدل پروسیجرال، Exploded View، وضعیت نمایشگر (دوربین/طبقه/اتاق)، هندسهٔ مسیر، نگاشت GLB (منطق خالص)
- `tests/3d` — رندر واقعی صحنهٔ React Three Fiber با `@react-three/test-renderer` (بدون GPU): بارگذاری مدل، انتخاب طبقه، Exploded View، کلیک روی اتاق، رسم مسیر، بازنشانی دوربین
- `tests/security` — قواعد دسترسی ادمین، غیرفعال‌بودن ادمین دمو در production، وجود و منطق سیاست‌های RLS در `database/schema.sql`، نبود کلید service-role/رمز ثابت در کد
- `tests/theme.test.ts` — هم‌ترازی توکن‌های CSS و Three.js

محدودیت‌ها: رندر تصویری GPU/WebGL و رفتار لمسی با آزمون خودکار پوشش داده نمی‌شود (مسیرهای کاربری در Chrome headless به‌صورت دستی بررسی شد، نه به‌عنوان e2e داخل مخزن). سیاست‌های RLS فقط به‌صورت ایستا (تحلیل متن SQL) آزموده می‌شوند، نه روی پایگاه‌دادهٔ زنده.

## محدودیت‌های فعلی

- همهٔ داده‌ها و مدل ساختمان **نمونه** هستند؛ منتظر نقشه‌های DWG/DXF و داده‌های تأییدشده است.
- موقعیت‌یابی زنده یا خودکار داخل ساختمان (GPS و …) وجود ندارد؛ نقطهٔ شروع دستی است.
- پنل دموی محلی فقط برای توسعه است، امنیت ندارد و در تولید کار نمی‌کند.
- ویرایشگر بصری گراف مسیر نیست؛ گره‌ها و یال‌ها با جدول/فرم اعتبارسنجی‌شده ویرایش می‌شوند.
